# Shared Eden routes: one setup library for every lane

2026-11-16. `tools/eden-runner/routes.py` (Training and menus) and `routes_online.py` (pairs) hold the setup
blocks every Eden row reuses. Before them, each lane hand-built its boot route and fixtures. On 2026-11-15 the
TrainingRooms rc.15 lanes and the Online Deluxe lane lost more than eight boots to setup mistakes this playbook
already covered ([HARNESS-LESSONS](HARNESS-LESSONS.md)).

## What is proven, and when to use it

- **Proven hosts** (2026-11-16, "Proof" below): the XPS and the Surface (Linux) and the Ally (Windows). The Yoga
  hasn't booted these blocks; its proof boot was deferred because the feature lanes have slot priority. Proven
  blocks:
  - `configure_boot`, `load_game`, `wait_lines`, `to_main`;
  - `main_to_stage`, `pick_stage` (by name);
  - `pick_fighters` for P1 only;
  - `enter_training`, `chord`, `fixture`, `back_to_main`.
- **Not proven:** the CPU's coin on the CSS, damage cleared from above 0, and the online blocks.
- **A lane's first proof boot** may reuse a route that already passed for it, verbatim; for TrainingRooms that is
  rc15-integration remaining-2's boot → Training (no CSS/SSS walk). Use the blocks for the rows after it, for
  example a stage by name or a fixture per row.
- **A one-off Eden glitch is not a route bug.** Down, rerun once, and note it. Change a block only when the failure
  repeats.

## How to call a block

A block is a runner step hook. A row names it with `routes:` and no path:

```json
{"run": "routes:pick_stage", "args": {"stage": "Battlefield"}, "check": true}
```

- Every block checks the screen it starts on, so it never trusts a gate from an earlier screen.
- Every block waits on game state with a cap: Eden `status`, a plugin line, a tile-cursor line or an image gate.
  It sleeps a fixed time only where no state exists.
- Every block ends on a still in the row folder and returns a small receipt. Stills are reviewed after the run; a
  block never stops for a live review (the game would idle into its attract demo).
- Every block fails closed: a missing state raises with what was seen, and nothing guesses.

The data the blocks use is in `tools/eden-runner/library/routes/`:

- `index.json`: the macros, each with its sha256 and source. `routes.play()` refuses a file whose hash differs.
- `tables.json`: fighter kinds by CSS tile and stage ids by stage-select tile. It is generated by `build_tables.py`
  from TrainingRooms' own `roster_grid.rs` and `lobby_stages.rs`, never from memory.

## The blocks

| Block | Starts on | Guarantees on exit |
| --- | --- | --- |
| `configure_boot` `{gdb_port}` | frontend, no game (lifecycle `defer_load`) | volume 0, `memory_layout_mode` 0 and (with `gdb_port`) the GDB stub on, each set, read back and saved |
| `load_game` `{gdb_port}` | the same | the game loaded: no-hold kick (`?`, `c`, close without a detach) **before** any wait; then `loading_complete`, no shaders building, at least 30 FPS |
| `wait_lines` `{lines: [[source, regex]]}` | any | each boot line is present, for example TrainingRooms' `result=installed`. Use it instead of a fixed post-load sleep. A source may be `sdmc:<path>` |
| `to_main` | title, opening, attract demo, How to Play, or main | the main menu (library `main` gate). Start is pressed at once when the gate misses, up to 8 times |
| `main_to_stage` | anywhere `to_main` handles | Training's stage select (`stage` gate) |
| `pick_stage` `{stage, allow_derived}` | stage select | the named stage's tile settled (`at` equals `to`), A pressed, the character select (`css` gate). An unproven tile needs `allow_derived` and the stage-id check after the load |
| `pick_fighters` `{p1}` | character select, P1's token in the hand | P1's token on its tile (`hovered` equals `at`) and placed. The CPU stays as it was; see "The CPU's coin" |
| `enter_training` | both placed | Training: fresh state lines for both bodies, the HUD gate (a first-run tip is closed with A) |
| `chord` `{name}` | Training | the chord pressed in one frame, and for `tr-save`/`tr-load` TrainingRooms' `state saved`/`state placed` line after it |
| `fixture` `{p1, cpu, stage, reset, damage, lr}` | Training | kinds, stage id, damage and facing read from game state and asserted; after the native L+R+A reset, both bodies grounded and waiting, x/y unchanged on two fresh reads |
| `back_to_main` | Training, a select, or a menu | (from Training) native pause and Quit, then a held B out of each select, until the `main` gate passes |

`pick_stage` and `pick_fighters` step the tile cursor ([TILE-CURSOR](TILE-CURSOR.md)) with the `tile-*` macros,
never a plain D-pad. Each step must log `step … to=N`, then `settled … at=N`. Row widths come from the log, not
from a constant.

### The CPU's coin: not proven

The CPU's coin rests on the Random tile, the last one. Picking it up needs the empty hand moved onto it with the
analog stick. On 2026-11-16 four approaches on the XPS (`harness-lib-xps-1`, r05) failed:
1. **From Mii Gunner (tile 85):** P1 placed there, then six 6-frame pushes right, each followed by A. The first A
   started Training (Mii Gunner against a random Daisy).
2. **lr-04's recorded route from Steve (78):** `lr04-cpu-approach` and `lr04-cpu-pick` (right 26 and 20 frames,
   down 14 and 18, then A) left the hand on the CPU panel below the coin. The A did nothing.
3. **The same two right pushes with no down push** (`coin-pick`, first version): the A started Training.
4. **The same with 10 frames down:** the A started Training.

Each started Training because P1 was placed and the screen was ready to fight, so an A that misses the coin starts
the match.

`pick_fighters` therefore refuses a `cpu` argument unless `coin_route` is true, which is for testing a route only.
Set the CPU with the lane's own fixture and assert it with `fixture {"cpu": …}`.

## Game state (TrainingRooms diag build)

- **Bodies:** `read_state` writes `diag-pos.req` beside `settings.json`. TrainingRooms answers with
  `[TrainingRooms] state pos entry=N kind= x= y= lr= dmg= status= situation=`, where entry 0 is P1 and entry 1 is
  the CPU. Only lines after the request count.
- **Stage:** the stage id comes from the camera lines `[TrainingRooms] cpu_event camera_setup|camera_mode … stage=N`.
- **Settled:** status 0 and situation 0, with x/y unchanged across two fresh reads, as in remaining-2-d1's approved
  predicate. That predicate covered P1 only; this one covers both bodies.
- **Tracing:** with the GDB stub on, tracing is off, so these reads come from the plugin's lines.

## Logs that rotate

`routes.LogCursor(path)` keeps the file it started on open:
- **Rotation:** on a rename it drains the old file, then reads the new one from its start.
- **Truncation:** when the file shrinks, it reads from 0.
- **Waiting:** `wait(regex, cap)` returns the first new matching line and keeps later lines for the next wait.

Use it for any plugin log a wait reads. TrainingRooms' `practice-diagnostics.log` rotates at 128 KiB.

## Online pairs (`routes_online`)

These checks are taken from the runs that passed: runtime-calibration-4 (LAN, 2026-11-15) and
eden-ldn-coexistence runtime-12/13 (Local Wireless). They have not been booted again as blocks.

- **`lan_leader`:** after A's `game.load`, A's console shows:
  - one `[auto] broker started … local_only=false`;
  - one `[coord] leading`;
  - one `[auto] ready pid=P`;
  - `member joined pid=P … members=1`.
- **`lan_pair`:** after B's `game.load`, A's last `members=` is 2 with B's ready pid, and B has no `leading` line.
  If B leads its own room, the block fails, and both instances go Down before Quickplay.

- **`ldn_join`** keeps native Join closed until an exact-release trace qualifies
  the selected native list row, the associated scan key and refresh generation,
  and the backing record consumed by Join. The pinned guest request and host
  approval macros remain historical setup evidence.
- **`ldn_pick_fighter`** selects a named fighter from a verified native CSS
  belonging to the local host or guest. The later L+R Start is a distinct action.

## A real Switch (the same rows, the pad and OBS)

Rows for the console use the same `rows.json` format, segments, gates and `routes:` hooks as Eden. Only the
instance differs, and every input is a macro (no manual presses).

```text
/usr/bin/python3 -I tools/eden-runner/recipe_macro.py rows.json            # recipes -> .edenmacro.json + sha256
/usr/bin/python3 -I tools/eden-runner/runner.py dry-run rows.json          # READY before the console
/usr/bin/python3 -I tools/eden-runner/switch_hw.py up <run dir>            # claim, pad, OBS, live Skyline log
/usr/bin/python3 -I tools/eden-runner/runner.py run rows.json --instances <run dir>/instances.json --out <run dir>/out
/usr/bin/python3 -I tools/eden-runner/switch_hw.py down <run dir>          # always
```

- **Input:** `usb:///dev/ttyACM0` (the ESP32-S3 pad, switch-pad 0.1.2) goes to switch-remote's client
  (`SWITCH_REMOTE_DIR`, default `~/ssbu-switch-remote/tools/host`).
  - `macro.play` uploads the Eden macro with `MBEGIN`/`MEV` and the pad plays it at 60 Hz of its own clock, so
    same-frame chords stay same-frame.
  - The client pings every 300 ms; the pad's 1 s watchdog then never fires mid-macro.
  - HOME and Capture are refused inside macros; the `switch_boot` and `switch_close` hooks press them.
- **Recipes:** `recipe_macro.py` compiles them offline. `b+up` is one frame, and every hold is at least 2 frames.
  The runner never records on hardware.
- **Logs:** `switch_hw.py` captures Skyline's TCP log (`192.168.0.224:6969`) one complete line at a time into the
  instance's `console_log`, so log gates and `LogCursor` work as on Eden.
  - The card runs the RELEASE NRO: TrainingRooms prints its install line and `cpu_common_load` there, and no diag
    lines. Menus and Training need image gates.
  - SD files (`events.log`, settings) are FTP reads after the session, not live gates.
- **Images:** `ui.screenshot` is an OBS still of the capture card. The `routes` gates read it against `hw-*`
  references (`library/routes/refs/`), cut from the reviewed switch-hw-ledger-rc15 stills:
  - each one passes on its own screen and fails on the others (`hw-refs.json`);
  - the Eden references don't apply there (window grabs are 1280x674; the card is a true 16:9 frame).
- **Auto-dim (a calibration on the operator's review list):** after about 5 min without input the console dims
  its screen to about 1/3.
  - When the plain compare fails, the `hw-*` gates compare again with the ROI lifted to the reference's brightness
    (gain 1.3–4).
  - Every pass also needs a third of the reference's contrast, so a flat frame can't pass.
  - `test_routes.py` (SwitchDiscriminationTests) pins it: each gate passes only its own screen, at normal and
    dimmed brightness; every other gate's content at its ROI fails, HOME vs main vs TR menu vs HUD included.
  - **The root alternative:** stop the console from dimming. That's a console setting, and the operator's choice.
- **One recording per session** (plan key `"session_recording": {"marks": ["row-start", "row-end", "shot"],
  "chapters": true, "log": "recording.jsonl"}`), instead of a `gif` step per moment, which cost about 7 s each on
  hardware.
  - **Start and stop:** the runner starts the backend's session recording before the first executed row and stops
    it in `run()`'s `finally`. The backend is switch-remote's `recording.session_*`, over OBS.
  - **Marks:** every executed row is marked at its start and end (failed rows included), and so is every `shot`
    step. Each mark is one JSON line in `<out>/recording.jsonl` (`event`, `row`, `label`, `wall`, `rec_ms`,
    `frame`). Receipts carry `rec_ms: [start, end]`. Clips and stills are cut from the one recording afterwards.
  - **If the runner died:** `switch_hw.py down` stops a recording that this run started and never stopped. OBS is
    shared, so nothing else is touched.
  - **Clips:** `/usr/bin/python3 tools/eden-runner/cut_session.py <out> [--only gifs|rows|stills]` cuts each clip from
    the recording into its preset. It needs PyGObject/GStreamer, so run it without `-I`. Live proof: live-rec-1,
    2026-11-16.
  - **Backends without it:** the run goes on without a session recording. Eden has no `recording.session_*`
    methods today.
  - **One file per row** (`"per_row_files": true`, optional `"split_cap_s": 10`): the row-start mark becomes a
    split (`recording.session_split`: OBS `SplitRecordFile`, then the `RecordFileChanged` event). OBS splits at its
    next keyframe, so the row's input waits for the event. The file that began at row N's split is row N's clip;
    it closes at the next split or at the stop (a failed or interrupted row too). Then the runner hard-links it
    to `<out>/<row>/clip.mp4`, puts `clip` in the row's receipt, and logs a `clip` event in `recording.jsonl`.
    `cut_session.py` then cuts each row's GIFs and stills from its own clip.
    - **A split with no event within the cap fails loudly:** the row-start mark carries `split.ok: false`, the
      row gets no clip, and the open file goes on to hold that row too (`rows` in its `clip` event). There's
      never a Start/Stop instead mid-session: that race was F04 (obs_500/501).
    - **Precondition:** OBS's record output needs manual splitting on. Simple output mode has no UI for it, and
      it resets when OBS restarts or Settings > Output is applied. `switch_hw.py up` checks it and refuses while
      it's off. The fix is `obsws.py split-enable` (switch-remote tools/host); `up --allow-no-split` runs without
      it. The runner itself never changes OBS settings.
- **The bridge NRO (optional, 2026-11-17):** with the test-only `ssbu-hw-bridge` installed beside TrainingRooms,
  `switch_hw.py up <run> --bridge-host 192.168.0.224[:6970]` gives the instance Eden's keys too: `diag_log` is
  `<run>/bridge.log` (TR's own oracle lines plus ` frame= wall=`, also appended to `console_log`), `settings` is
  `<run>/bridge/settings.json` (fetched after every `settings.json written` line), and the folder beside it is a
  request spool where `diag-pos.req`, `diag-save.req`, `diag-load.req`, `diag-item.req` and `diag-settings-next.json`
  become the bridge's `pos`, `save`, `load`, `item`, `set` requests. So `read_state`, settings fixtures and log gates run
  as on Eden. `switch_hw.py state <run> [--fresh pos,speed,roster,status]` (or `switch_hw.bridge_state(run, fresh)` in
  a row) returns the console's newest B-FRAME, B-POS (both bodies), B-STAGE, B-ROSTER, B-ITEM, B-SPEED and
  B-STATUS-NAMES as JSON, without an OBS still; `--fresh` asks the bridge first and waits for the answers. In a row,
  `routes.native_state(ctx, fresh)`, `routes.wait_native(ctx, test, cap)` and `routes.frame_advancing(ctx)` read the
  same through the instance's `bridge_log`. Design:
  `ssbu-hw-bridge/docs/DESIGN.md`.
- **One driver per console:** `up` refuses while any process holds the tty or the claim file
  (`~/.cache/switch-pad.claim`) exists. `down` sends RESET, stops the log capture and removes the claim.
- **Hardware blocks:**
  - `switch_boot`: B, HOME, the SSBU tile gate, A, the profile A, then Start until the main menu.
  - `switch_to_training` starts from the native Games & More hover or the Training
    submenu item. It confirms the Training stage, verifies local fighter placement
    and checks native Training and the loaded stage kind. The native route
    requires a new gameplay stage event after the CSS launch checkpoint.
    It verifies same-boot event replay and rejects gaps, reconnects and old
    event clocks. If the bridge emits no event on a same-stage return,
    the route stops. A repeatable proof needs a new gameplay stage receipt
    for every loaded Training battle, even when the numeric ID is unchanged.
    Supply `p1` and
    `fighter_topology` when a named pick needs movement from an off-grid hand.
  - `tr_menu`: `preload_clear`, B+Up, the menu gate, B and B, the HUD gate.
  - `preload_clear` (`{"run": "routes:preload_clear"}`, or `routes.preload_clear(ctx)` from a hook, on the
    Training HUD before any menu input):
    - **Why:** TR's preloader builds the planned fighters after a Training scene starts, and pad input sent
      meanwhile is lost. In `switch-hw-session-1` T-01 (15:03Z), an R into the TR menu was lost at "Loading 4/7",
      12 s after the HUD.
    - **What it gates on:** the notice in the middle of the screen. "Fighters / Loading n/m" means it's still
      working. Any other "Fighters" state ("Ready 8/8", "All loaded (..)", "Loaded n/m", "Swap .. to load") means
      it's done.
    - **An absent box proves nothing.** The box disappears between steps (90 frames per state), and the HUD comes
      up about 3 s before the first step. The release build logs none of it.
    - **No preload:** with no Loading notice within `appear` (10 s) and no `[NRO hook] Loaded` line meanwhile,
      the gate passes.
    - **Later calls:** a pass is kept in `out/routes-preload.json`, so later calls pass at once until the log
      gains a `[NRO hook] Loaded` line (a new scene or a fighter change).
    - **References and proof:** `hw-notice-fighters`, `hw-notice-loading` (from a session-1 frame). Host-tested
      on synthetic frames, and checked against the session's real frames (Loading 3/7 and 4/7, Ready 8/8, a
      minigame notice, the HUD, the menu). It hasn't run live yet, and it's unproven on Eden.
  - `switch_close`: HOME, X, then A on the close dialog.
  - `pick_stage_hw {stage}` and `pick_fighter_hw {p1}` prepare a verified hover.
    `confirm_pick {expect}` rechecks the same idle checkpoint within the runner
    instance and sends A. CSS confirms the local token placement. SSS confirms
    the native destination screen, configured with `next_screen` when needed.
  - `pick_stage`, `pick_fighters` and `routes_online:ldn_pick_fighter` use the
    shared state-backed picker when the bridge supplies the native state.
    CSS form defaults to `default` and SSS form defaults to `normal`.
  - A `topology` argument pins an independently qualified JSON capture with
    its `path` and `sha256`. The capture contains `layout` (the exact live fingerprint),
    `neighbors` (tile-to-direction-to-tile mappings) and `targets` (tile keys
    mapped to exact `kind`, `name` and `form`). Use decimal string tile keys
    and `none` as a source only for a verified position below the grid.
    A pick on the correct settled tile needs no movement map.
  - Hardware and paired Eden release qualification remain open. See
    [Native UI state and tile cursor providers](/home/intpa/ssbu-hw-bridge/docs/NATIVE-UI-STATE.md)
    for the rollout gates.
